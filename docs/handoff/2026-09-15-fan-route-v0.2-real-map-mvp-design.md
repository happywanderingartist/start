# 星迹 v0.2｜真实地图路线 MVP PRD

- 文档状态：产品负责人已确认，进入实施计划阶段
- 版本：v0.2
- 日期：2026-09-15
- 适用载体：手机网页
- 核心路线：安溥·南京老城巷陌

## 1. 版本背景

v0.1 已打通“首页—路线详情—路线进行中—外部地图模拟—返回继续”的可运行原型，但地点、距离、时长与地图跳转仍为模拟数据。该版本可以证明交互链路可实现，不能证明产品已经解决用户在小红书和地图之间反复切换、逐点输入地点的问题。

v0.2 将产品从“可点击演示”推进到“真实地图数据驱动的可测试 MVP”。本轮只验证一个核心假设：用户能否在星迹中理解、调整并复刻一条真实路线，且比自行在内容平台与地图之间整理更省事。

## 2. 目标与非目标

### 2.1 版本目标

1. 用真实 POI 替换手填地点数据。
2. 用地图算路结果生成相邻站点的距离、预计时长与交通方式。
3. 用户调整地点顺序、删除或跳过地点后，受影响路段自动重新计算。
4. 用户可选择高德或百度作为导航出口，无需重新输入地点。
5. 完成至少 5 名目标用户的任务测试，验证核心路线闭环。

### 2.2 成功标准

- 5 名目标用户中，至少 4 人无需口头指导完成“查看路线—调整一个地点—开始路线—打开地图—返回—完成第一站”。
- POI 确认后的导航目标与路线作者选择的实体地点一致率为 100%。
- 所有展示的距离和交通时长均能追溯到地图服务商、计算时间与起终点 POI。
- 用户调整路线后，所有新增相邻路段均重新计算，不沿用失效结果。
- 用户无需在外部地图中重新搜索或输入下一站名称。

### 2.3 本轮不做

- 不做小红书链接抓取、图片 OCR 或完整多模态 AI 解析。
- 不做 AI 自动决定 POI；AI 只能在后续版本提供地点候选。
- 不做社区首页、关注关系、评论、聊天和物料交易。
- 不做账号系统和跨设备同步。
- 不同时维护高德、百度两套算路结果。
- 不承诺把多站步行路线一次性导入所有地图 App。
- 不做实时位置共享和自动判断用户是否到站。

## 3. 核心决策

### 3.1 地图能力分层

地图能力拆成三个独立层级：

1. **数据计算层**：高德 Web Service API 提供 POI、距离、交通方式和预计时长。
2. **产品呈现层**：星迹展示地点卡片、相邻路段和完整路线进度；可选增加高德地图概览，但不依赖地图组件完成核心任务。
3. **外部导航层**：根据用户选择生成高德或百度地图的调起链接。

星迹保存完整路线、调整结果和用户进度；外部地图只承担当前路段导航。

### 3.2 数据提供方

- v0.2 以高德作为唯一标准 POI 与算路数据源。
- 路线页必须显示“距离与预计时长由高德地图数据计算，实际导航结果以所选地图为准”。
- 高德路径规划 2.0 返回步行、公交、驾车或骑行方案中的距离与预计时长。
- 百度仅作为导航出口，不参与 v0.2 的路线指标计算。

### 3.3 坐标体系

- 产品内部标准坐标使用 GCJ-02，并记录 `coordinateSystem: "gcj02"`。
- 高德导航直接使用 GCJ-02 坐标和高德 POI ID。
- 调起百度地图时显式传递 `coord_type=gcj02`；不得把 GCJ-02 当作默认 BD-09 坐标使用。
- 不自行实现未经地图服务商确认的坐标转换算法。

## 4. 用户流程

### 4.1 路线创建者确认地点

1. 创建者输入地点关键词和城市。
2. 系统通过服务端调用高德 POI 搜索。
3. 页面展示候选地点的标准名称、地址、行政区和类别。
4. 创建者选择一个候选地点后，系统保存高德 POI ID、GCJ-02 坐标、标准名称与地址。
5. 没有合适候选时，创建者修改关键词重新搜索；不得跳过确认直接发布。

v0.2 不开放公共路线发布，因此该流程先作为内部路线制作工具或受控编辑页面使用。

### 4.2 生成路线

1. 系统按照地点顺序拆成相邻路段。
2. 服务端分别请求步行方案；当步行时间超过 30 分钟或距离超过 2 公里时，再请求公交方案。
3. 默认展示地图返回的首选方案，并允许路线创建者在可用方案中切换交通方式。
4. 保存每个路段的起终点、方式、距离、时长、数据提供方与计算时间。
5. 计算路线交通总时长；地点停留时间单独保存，不与地图交通时长混淆。

### 4.3 调整路线

用户可以：

- 拖动地点调整顺序；
- 删除尚未到达的地点；
- 将尚未到达的地点标记为“本次跳过”。

调整确认后，只重新计算被改变的相邻路段。例如删除 B 后，A→B 与 B→C 失效，系统新增并计算 A→C。已完成站点不得拖到当前站点之后，避免破坏进度语义。

“添加新地点”在 v0.2 受控测试版本中只允许从已确认 POI 搜索结果添加，不保存自由文本地点。

### 4.4 开始与继续路线

1. 用户选择高德或百度地图，可选择记住偏好。
2. 第一站按钮显示“导航到{当前地点名}”，不得使用“导航下一站”。
3. 点击后自动生成当前站点的地图调起链接。
4. 用户从外部地图返回后，星迹仍保留完整路线与当前进度。
5. 用户点击“已到达”，产品推进到下一站。
6. 下一步主按钮显示“导航到{下一地点名}”。

不要求用户重新搜索、复制地址或重新选择地点。自动到站判断和后台定位不在本轮范围内。

## 5. 页面与交互变化

### 5.1 首页

- AI 输入框改为“路线搜索/示例匹配”状态，明确说明当前只能从已有路线中匹配。
- 任意非空输入不得伪装成 AI 已理解；不匹配时显示无结果，并提供查看已有路线入口。
- “搜路线”必须进入实际搜索状态或路线列表，不再只滚动到唯一推荐卡片。

### 5.2 路线详情页

- 展示真实城市、站点数、交通总时长和建议总时长。
- 每个地点使用独立图片、故事与打卡信息，不复用同一张抽象图作为主要内容。
- 相邻地点之间展示交通方式、距离、预计时长、数据来源和计算时间。
- “调整路线”打开可用编辑界面，不再展示“后续开放”的死端弹层。
- 数据不可用时保留最近一次成功结果，并显示“暂时无法更新”。

### 5.3 路线进行中

- 当前地点与下一地点必须区分清楚。
- 主按钮始终带入具体地点名。
- 返回后无需重新选择地图或地点。
- 路线调整只允许影响未完成站点。
- 完成全部站点后进入完成页；纪念小卡仅保留预告，不在本轮生成。

## 6. 服务与接口

地图密钥只能保存在服务端环境变量中，禁止写入前端源码或提交到仓库。

### 6.1 接口清单

#### `GET /api/places/search`

输入：`keyword`、`city`。

输出：最多 10 个标准化 POI 候选，包括 `providerPoiId`、名称、地址、行政区、类别、经纬度和坐标系。

#### `POST /api/places/confirm`

输入：被选择的 POI 候选。

输出：标准化 `Place` 对象。服务端重新检查关键字段，不能直接信任前端提交的坐标。

#### `POST /api/routes/calculate`

输入：有序 Place ID 列表、用户选择的交通偏好。

输出：相邻路段列表、交通总距离、交通总时长、计算时间与数据状态。

#### `POST /api/routes/recalculate`

输入：旧路线版本、新地点顺序和受影响路段。

输出：新路线版本及重算后的相邻路段。请求必须具有幂等标识，防止拖动或重复点击造成多次写入。

### 6.2 服务端职责

- 保管 `AMAP_WEB_SERVICE_KEY`。
- 统一高德返回字段为产品内部数据结构。
- 以“接口类型＋起终点 POI＋交通方式”作为缓存键。
- 处理接口超时、限流、无结果和服务商错误码。
- 记录匿名调用次数、缓存命中和失败类型，不记录用户精确实时位置。

## 7. 核心数据结构

```ts
type CoordinateSystem = "gcj02";
type TravelMode = "walk" | "transit" | "drive" | "ride";

interface Place {
  id: string;
  city: string;
  name: string;
  address: string;
  provider: "amap";
  providerPoiId: string;
  coordinateSystem: CoordinateSystem;
  longitude: number;
  latitude: number;
  verificationStatus: "confirmed";
}

interface RouteLeg {
  id: string;
  fromPlaceId: string;
  toPlaceId: string;
  mode: TravelMode;
  distanceMeters: number;
  durationSeconds: number;
  provider: "amap";
  computedAt: string;
  dataStatus: "fresh" | "cached" | "unavailable";
}

interface RouteStop {
  placeId: string;
  order: number;
  suggestedStayMinutes: number;
  visitStatus: "upcoming" | "current" | "arrived" | "skipped";
  story: string;
  checkInTips: string[];
  imageUrls: string[];
}

interface FanRoute {
  id: string;
  version: number;
  title: string;
  city: string;
  artist: string;
  stops: RouteStop[];
  legs: RouteLeg[];
  travelDurationSeconds: number;
  suggestedStayMinutes: number;
  computedAt: string;
}
```

## 8. 缓存、刷新与降级

- POI 确认结果随路线版本保存；路线编辑者主动更换 POI 或地点被举报错误时重新确认。
- 步行、骑行和驾车路段缓存 30 天；公交路段缓存 24 小时。
- 用户开始路线时，后台异步刷新过期路段；刷新完成前可展示缓存值并标注更新时间。
- 接口失败但存在缓存时，使用缓存并显示“暂时无法更新，以地图导航为准”。
- 接口失败且无缓存时，不展示虚构数字；路段显示“距离与时长暂不可用”，仍允许打开外部地图。
- POI 搜索无结果时要求重新输入，不允许生成只有名称、没有坐标的路线站点。

## 9. 安全、隐私与成本控制

- 高德 Key 只存在服务端环境变量中。
- 前端只提交地点关键词、城市、POI 选择和路线顺序。
- v0.2 不读取持续定位，不收集用户运动轨迹。
- 服务端对搜索与算路接口设置请求频率限制。
- 对相同路线版本优先读取缓存，避免每次打开页面都重新算路。
- 开发前在高德控制台确认账户的日调用额度与 QPS；超过额度时不得无提示地回退为假数据。

## 10. 埋点与验证

### 10.1 核心事件

- `route_search_submitted`
- `route_search_result_opened`
- `route_adjust_started`
- `route_adjust_saved`
- `map_provider_selected`
- `navigation_opened`
- `route_returned_from_map`
- `stop_marked_arrived`
- `route_completed`
- `map_api_failed`

埋点不写入姓名、粉籍、实时坐标或完整搜索原文；测试阶段以匿名会话 ID 关联同一次任务。

### 10.2 用户测试任务

1. 找到“安溥·南京老城巷陌”。
2. 查看一个地点的故事与打卡提示。
3. 删除、跳过或调整一个尚未到达的地点。
4. 选择地图并导航到第一站。
5. 返回星迹并完成第一站。

记录任务完成率、完成时间、误触点、用户原话，以及用户是否认为该流程比自行整理内容平台和地图更方便。

## 11. 验收标准

### 11.1 地点与算路

- [ ] 安溥南京路线的每个地点都绑定已确认的高德 POI ID。
- [ ] 每个相邻路段展示真实距离、时长、方式、提供方和计算时间。
- [ ] 删除或调整地点后，失效路段被移除，新路段重新计算。
- [ ] 地图接口无结果时页面不展示模拟数字。

### 11.2 导航

- [ ] 用户可选择高德或百度。
- [ ] 高德与百度均能打开正确的当前目的地。
- [ ] 百度调起链接显式声明 GCJ-02 坐标类型。
- [ ] 从外部地图返回后，路线顺序、地图偏好与完成进度保持不变。
- [ ] 用户不需要复制地址或重新输入地点。

### 11.3 交互与可靠性

- [ ] 空搜索、无 POI、接口超时、限流和无缓存均有明确状态。
- [ ] 计算和保存过程中禁止重复提交。
- [ ] 路线编辑与算路失败时保留上一版有效路线。
- [ ] 所有主要按钮名称与实际目标一致。
- [ ] 390×844 视口无横向溢出，固定操作区不遮挡路线内容。
- [ ] 键盘可操作主要控件；弹层支持焦点进入、焦点限制、Escape 关闭和关闭后焦点恢复。

### 11.4 工程验证

- [ ] POI 标准化、路段重算、缓存降级和进度迁移均有自动化测试。
- [ ] 地图 API 使用可替换的适配层，测试环境不消耗真实调用额度。
- [ ] TypeScript 类型检查、测试与生产构建全部通过。
- [ ] 使用真实 Key 完成一次安溥南京全路线端到端验收。

## 12. 开发拆分

### 里程碑 1：地图数据基础

完成服务端地图适配、POI 搜索、地点确认、相邻路段计算、缓存与错误标准化。

### 里程碑 2：真实路线详情

将安溥南京路线替换为真实 POI 与路段数据，修正首页承诺和路线详情页信息结构。

### 里程碑 3：调整与导航

完成删除、跳过、排序、局部重算，以及高德/百度当前站点导航。

### 里程碑 4：测试与迭代

完成自动化验收、5 名目标用户任务测试，并依据证据调整下一版范围。

## 14. 求职证据边界

本 PRD 可以证明需求拆解、平台能力分层、地图技术选型、数据建模、异常设计与验收设计能力。它不能证明真实地图已经接入、用户测试已经完成或效率已经提升。

只有在真实接口、端到端验收和目标用户测试完成后，才可以将结果写成项目成果；开发前的内容统一表述为产品决策、设计方案和验证计划。
