# Fan-route 开源项目采纳矩阵

状态：v0.3 产品架构提案的研究输入，不代表已经引入任何第三方代码。

## 采纳原则

Fan-route 复用成熟项目解决问题的方法，不整体 Fork，不以星标代替代码审查，不把参考项目的功能边界原样搬进产品。每次采纳都必须说明用户问题、参考来源、复用层级、许可证、退出方式和验证证据。

复用层级固定为四档：

1. `pattern`：只学习产品模式、领域边界或交互逻辑，独立实现。
2. `interface`：复用接口形状、数据流和适配器思想，使用 Fan-route 命名与测试重新实现。
3. `dependency`：通过包管理器引入许可证清晰、维护活跃、范围稳定的依赖。
4. `source`：移植少量边界明确的源代码；必须先完成许可证和来源记录，并补 Fan-route 自己的测试。

默认优先级为 `pattern > interface > dependency > source`。GPL、AGPL 或许可证不明的项目只允许 `pattern` 和独立实现，除非产品负责人明确接受对应开源义务。

## Fan-route 采纳清单

### 立即采用

- 按业务能力垂直切片，而不是继续按 `pages/components/data/state` 横向堆叠。
- `Route`、`RouteVersion` 与 `Journey` 分离；公共路线更新不能改变进行中的用户旅程。
- 地图、路线列表和地点详情读取同一领域数据，不维护三套展示模型。
- 高德作为当前标准源，但通过 `MapProvider` 隔离；页面不读取高德原始字段。
- 所有路线修改带 `baseVersion` 和 `idempotencyKey`；失败保留上一版成功路线。
- AI 只能生成可编辑草稿，不能直接发布路线或猜测 POI。
- 娃娃资产使用 Manifest、槽位和固定锚点；渲染器不负责生成资产。

### 暂不采用

- 微服务、插件系统、完整事件溯源、多人实时协作。
- 预算、预订、行李、天气、复杂日历和固定时间表。
- 自建地图与算路引擎。
- 多娃商城、复杂社交关系、即时聊天和支付。
