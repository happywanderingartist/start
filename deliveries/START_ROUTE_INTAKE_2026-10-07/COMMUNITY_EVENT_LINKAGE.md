# 社群、演出、场馆与物料联通 · 结构讨论记录

2026-10-07。用户要求核对尚不明确的产品结构，并提出艺人社群包含物料交换、地点及路线推荐，演唱会与真实地址、物料交换关联。当前暂停页面开发，只梳理结构；以下明确区分需求、已确认规则与建议，未写入数据库或实现API。

## 用户明确的内容关系

艺人页展示相关路线与打卡地点，可按城市和类别筛选。加入/关注艺人社群形成兴趣信号；社群内同时可浏览该艺人的地点、路线、活动、演出和物料集市。首页根据当前/选定城市优先结合这些兴趣推荐。社群展示同一套经审核地点与路线，不另建一套与艺人页脱节的地点数据。

演出保存演出ID、参与艺人、时间/状态，以及场馆地点ID、城市。一处场馆可有多场演出；一场演出可含多位艺人。物料若与演出相关，引用具体演出ID和所属社群；城市/场馆信息从该演出关系取得。地点详情可以查此场馆的近期演出；演出详情可进入场馆地图、相关社群、该场物料集市，以及经过该地点的已发布路线。场馆承办某艺人未来演出不等于艺人已经到访打卡，关系类型和状态分开。

示例仅为结构演示：上海某演唱会 → 对应真实场馆地点 → 参与艺人社群 → 此场演出的物料列表。数据源是同一份记录，不需要平台管理员在每个页面反复填写同一个地址。首页/艺人页/社群/地点页/物料页依各自筛选读取它。

## 延续已确认的规则（无需重复确认）

地点及艺人同款由平台审批后公开；艺人及演出资料平台维护，用户补充纠错经审批；社群用户申请、平台审批。社群管理员只管理简介、公告与成员，其他内容申请平台修改，不因社群内有地点/演出而获得主数据审批权限。

物料第一版线下交换，提供申请与接受，不含支付、邮寄、完整私信；平台不管理或认证交换是否完成，不设置完成确认。联系方式接受申请后双方自愿提供、仅双方可见、可撤回。演出关联不会让联系方式或私人Book变为公开。公开打卡内容与个人自由打卡记录分开，个人记录默认私密。

## 尚需明晰的产品决定与建议

1. 社群组织方式已确认：一个艺人只对应一个社群，不创建城市分社群或同艺人的多个主题社群。城市是该社群内地点、路线、演出和物料的筛选条件。用户仍可申请创建尚无社群的艺人社群，由平台审批；同艺人已有社群时进入已有社群。服务端须防止并发申请/审批产生重复社群。
2. 社群页主次：路线、地点、演出、集市和公告如何排布？建议社群总览突出该艺人的本城有效活动、路线和地点，提供明确模块入口；物料集市持续可见，不能因增加推荐被移走。此为待视觉确认布局提案。
3. 兴趣来源：加入/关注社群已经确认可影响推荐；是否另设艺人关注与音乐风格选择，以及退出社群后的兴趣保留方式仍需明确。建议加入状态与用户主动选择的兴趣分别记录，退出社群不默默抹掉用户其他显式偏好；界面给用户管理入口。
4. 物料关联范围：演出现场交换可绑定eventId；是否允许无演出的城市/日常交换仍需明确。建议演出关联可选，日常物料仍属于社群并填写城市；不能把物料集市全量强制归演唱会。
5. 演出场馆与交换集合点：两者不是同一字段。建议公开场馆/大致集合区域及必要时间；具体集合点的公开粒度待决定，联系方式保持既定私密规则。用户手填集合点不能覆盖演出场馆地址；不把分享演出等同于公开交换联系人。
6. 演出变更与物料状态已确认：公共演出资料更新后在相关页面显示最新资料；不因改期、取消或换场馆提醒物料发布者，也不自动改变其物料状态或集合安排。发布者自行选择物料状态，平台不追踪、干涉、验证或认证交换完成。不设双方完成确认，不根据接受申请自动扣减库存、转移所有权或认定完成；具体状态选项尚需视觉稿明确，发布者自报状态不等于平台认证。

部署地域/预算、微信AppID与权限、分享目的地/有效期、联系方式及日志保留期限、备份恢复目标仍是上线配置待确认，并非这次信息架构设计缺项。不重复询问已确认的登录、自由打卡、默认隐私、平台审批和无支付规则。

## 本次审查界限与参考

这是基于当前产品文档及用户澄清的信息结构核对，不是已实现界面的截图UX审查。读取product-design:audit后确认其要求真实界面捕获，不把它用于尚未存在的社群联动页面；采用Interaction Design分析模块关系、可见入口与状态变化。用户提供的“背着椅子跑”分类列表和地图展示作为参考，不声称本轮实际登录或完整操作了该小程序，也不据此判断其内部数据库设计。
